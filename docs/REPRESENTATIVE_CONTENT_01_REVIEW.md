# Representative Content 01 — independent pre-implementation review

**Date:** 2026-09-14
**Reviewed:** `REPRESENTATIVE_CONTENT_01.md` against current `main` architecture
**Verdict:** PASS WITH REQUIRED CORRECTIONS

## Review method

The pass was checked against the current content registry, progression invariants, `VerticalSliceApp`, `SquishSurface`, fragment shader, save normalization and the project roadmap. The review deliberately looked for hidden scope expansion, ID/save breakage, selector-state traps and renderer forks.

## 1. Scope verdict

The bounded four-recipe expansion is appropriate. It is large enough to test the high-CMF thesis and small enough to stop before catalog/UI production.

The following remain correctly out of scope:

- third shape;
- final recipe browser;
- full 24-item launch catalog;
- new craft stage;
- final card art;
- economy/ads;
- independent material renderer.

**PASS.**

## 2. Required correction — premium selection must not poison the legacy component selector

Current `VerticalSliceApp` stores a component choice and each shape/palette/filling button mutates only one field. A premium recipe selected from Collection can contain hidden palette/material/filling tokens that are not represented by the legacy selector.

If handlers simply preserve the other hidden fields, tapping one legacy component can create a non-canonical combination and then `getRequiredRank()` will throw.

### Required implementation rule

Any interaction with the legacy component selector must normalize back into the legacy recipe space:

- material becomes `soft`;
- hidden/non-legacy palette falls back to a visible legacy palette;
- hidden/non-legacy filling falls back to a visible legacy filling;
- resulting choice must resolve to a canonical old recipe before `updateSelectionUi()`.

Collection-launched premium recipes may remain selected after a craft/revisit, but component editing must be safe and deterministic.

**BLOCKER IF OMITTED.**

## 3. Required correction — canonical recipes must become explicit before adding non-Cartesian content

Current `ALL_VARIANTS` is generated by `SHAPES × PALETTES × FILLINGS`. Adding premium palette/material/filling tokens to those source arrays would silently explode the catalog and force progression coverage for unwanted combinations.

### Required implementation rule

- keep registries reusable;
- create explicit legacy selector subsets;
- generate the original 12 only from the legacy subsets;
- append exactly four explicit representative recipes;
- assert unique IDs.

This conversion must be covered by the progression table's existing exact-coverage invariant.

**BLOCKER IF OMITTED.**

## 4. Durable ID review

The old IDs are derived as:

- Soft Cube: `{palette}-{filling}`;
- Heart: `heart-{palette}-{filling}`.

Adding a material dimension must not change these IDs.

### Required implementation rule

`soft` legacy recipes retain the old ID format. New material recipes may include material in their IDs. Do not rename grape/strawberry/lime or smooth/beads IDs.

Save V2 does not need a schema bump because it stores opaque recipe IDs and the known-ID set is expanding rather than changing representation.

**PASS WITH ID PRESERVATION REQUIREMENT.**

## 5. Material architecture review

A small material profile layer (`soft`, `jelly`, `holo`) is preferable to burying effects in palette names or recipe-ID branches.

Required separation:

- palette owns color values;
- material owns bounded scalar style parameters;
- recipe choice composes both;
- renderer receives the merged style;
- shader sees only generic uniforms.

Do not create `if recipe == ...` or `if shape == ...` in shader/renderer code.

**PASS.**

## 6. Jelly alpha/readability risk

The renderer uses regular alpha blending over a very dark workspace. Aggressively lowering alpha can make the jelly look like a rendering bug rather than a tactile transparent toy.

### Required implementation rule

Use restrained translucency. Preserve silhouette/rim and internal glow; do not target physically correct transparency. The visual goal is "clear candy" readability, not optical simulation.

A phone visual check remains required after deployment.

**PRODUCT RISK, NOT STRUCTURAL BLOCKER.**

## 7. Holographic risk

A time-animated rainbow would add motion noise and can make the current premium lab presentation look cheap. It also creates another continuous-animation burden.

### Required implementation rule

Use a broad static spectral field modulated subtly by existing compression/strain state. No new time uniform is needed for this pass.

**PASS.**

## 8. Pearl artifact risk

Earlier foam artifacts came from using inconsistent cell transforms between bead occupancy and shading. Pearl work could accidentally reintroduce the same class of bug.

### Required implementation rule

Derive pearl/foam cell coordinates once from the same filling-style-dependent transform and use that cell for both reveal/occupancy and color/shading.

**BLOCKER IF GRID TRANSFORMS DIVERGE.**

## 9. Filling interaction review

Pearls do not justify a new interaction. The current add-stage progress is gesture-based and independent of bead visuals, so reuse is clean.

Required behavior:

- any non-smooth filling takes the add stage;
- filling style changes renderer appearance only;
- existing shake thresholds/timing remain untouched;
- copy becomes generic enough for both foam and pearls.

**PASS.**

## 10. Collection launch review

The current Collection only has actions for completed items. Premium recipes hidden from the legacy selector need a legitimate reachability path.

Adding **Make** to available cards is the smallest valid bridge and also improves the one-more loop. It must reuse the existing selected recipe + `setStage('pour')` path, not create a new craft mode.

**PASS.**

## 11. Progression review

Ranks 7/8 at 600/700 XP fit the current temporary +100 first-completion cadence and keep the representative recipes just beyond the existing rank-6 cap.

No final balance claim should be made. Existing users at 500 XP may need one more craft/repeat to cross Rank 7, which is acceptable for this test.

Required:

- extend the rank union/config only;
- keep old rank thresholds/unlocks unchanged;
- exact coverage invariant must cover 16 recipes.

**PASS.**

## 12. Milestone review

Current milestone code derives half/full counts from `ALL_VARIANTS` and derives shape sets from recipes belonging to each shape. It should adapt automatically to 16 if canonical content is explicit.

Do not add hardcoded 8/16 milestone literals outside tests/docs.

**PASS.**

## 13. Additional correction — palette naming in the spec

The recipe IDs use `prism-holo-*`, while the draft palette section proposed `opal`. This is unnecessary naming drift.

### Required correction

Use palette ID `prism` with working label such as **Opal Prism** so durable new IDs and config terminology line up.

**REQUIRED DOC/IMPLEMENTATION ALIGNMENT.**

## 14. Final implementation checklist

Implementation may proceed only if it satisfies all of these:

- explicit 16-recipe curated registry;
- original 12 IDs unchanged;
- selector subsets remain legacy-only;
- selector handlers normalize away hidden premium tokens;
- reusable material profiles, no recipe-ID shader branches;
- one shader program and one deformation mesh;
- generic add stage for foam + pearls;
- shared filling cell transform for occupancy + shading;
- Collection Make reuses current craft state machine;
- rank 7/8 exact coverage;
- SaveState V2 unchanged;
- strict typecheck/build and independent final diff review before merge;
- phone check required for jelly/holo/pearl visual quality.

With those corrections the pass is bounded, technically coherent, and aligned with the project's high-CMF production thesis.
