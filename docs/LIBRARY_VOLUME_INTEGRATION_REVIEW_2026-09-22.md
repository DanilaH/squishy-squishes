## Actual interactive craft/Squeeze volume — separate Pages-only integration

**Scope and ownership:** `/review/pr-59/` opts the existing `PhaserSquishSurface` into `PhaserSquishCandidate(..., pagesVolume=true)`; the normal candidate and production/Yandex paths keep the default `false`. `PhaserDeformableVolume` recomputes a shallow, continuous boundary strip from the **same live `SquishSimulation.projectUvToLocal`** in Phaser's existing WebGL2 context and frame loop. It does not render a static Library thumbnail per frame, allocate a second visible canvas, start another RAF, duplicate simulation state, alter hit testing, or touch the save codec. The strip starts only after the mold and fill have completed, so early craft transitions stay intact. Squeeze deforms the actual front and side together.

The Pages-only front fragment variant derives from the existing Studio GLSL: it softens the dark edge and adds modest smooth radial cap lighting. The side fragment samples the same current appearance texture and material colours; it is darker than the front but not a fixed brown/green cutout. Shared original `src/squish/shaders.ts`, core physics, input, original `/` and `/phaser/` behavior, and Yandex output are unchanged. Sidewall buffers and shader are disposed with the Phaser scene, and lost-context cleanup drops them for lazy recreation.

**Independent visual corrections:** The first live-browser pass had an overly dark lower band and a bright dotted line at the front/side transition. Reducing thickness and lightening the side improved the band. Moving the side's inner vertices up by 0.025 local units alone did **not** remove the bright line (the sampled centre-bottom pixel stayed unchanged). The actual cause was compositing order: rendering the side behind the antialiased front left a partially blended bright edge. Drawing the same dynamically deforming side **after** the front covers that fringe; the representative paw's centre-bottom transition became continuous in actual Chromium screenshots. Do not mistake the unused vertex-offset experiment for the fix, or generalize this visual result to all GPUs.

**Reproducible browser evidence:** [first interactive volume + three saved V3 toys](https://github.com/DanilaH/squishy-squishes/actions/runs/35774978109), [softened thickness and front overlap](https://github.com/DanilaH/squishy-squishes/actions/runs/35775382784), [draw-order correction with screenshot artifact](https://github.com/DanilaH/squishy-squishes/actions/runs/35776645212). In `tests/phaser-pages/library-hall-cross-scene-parity.spec.ts`, real user-like actions create a paw/crown/Soft, heart/Marshmallow and soft-square/Jelly, paint them, save V3, capture Studio idle, Squeeze idle/pressed/released, Hall thumbnail and reopened Squeeze, and check byte-identical V3 storage after reload, saved identity/material/paint/decor and JS exceptions. The sidewall screenshot is actual Phaser rendering, not a separate art mockup.

**Acceptance and rollback:** Run `npm run release:check`, `npm run qa:browser`, `npm run pages:qa`, dedicated Hall QA and candidate/Yandex regression on the final exact feature SHA. Inspect at least six shapes and six materials, crown/accessories, responsive layouts, context loss, and 30-second active/idle behavior. ## One consistent illustrated workshop through every craft step and Squeeze (2026-09-23)

**Owner-reported problems:** Squeeze had only a flat background, while the owner's actual Studio PNGs (wall, floor, shelf/plant, and three-part desk) appeared only on Shape and Paint. `studioEnvironmentPreview.ts` explicitly discarded them on Mixins, Mix, Decor, Finish and Squeeze. Stage-specific panel heights changed the canvas and desk geometry, visibly teleporting the toy/table/floor between steps. This was a shared layout/lifecycle issue, not a need to manually calibrate each step's `top`/`left`.

**Pages-only implementation:** `preloadStudioEnvironmentAssets()` decodes all existing owner images once and stitches the unmodified three desk slices at integer source coordinates before the playable maker starts. Failure falls back to the original UI with a warning; it must not block play. The same single passive DOM scene is retained across Shape → Paint → Mixins → Mix → Decor (including all three tab panels) → Finish → Squeeze, and on reopening a saved V3 toy. No new artistic substitute, extra visible WebGL context, independent RAF loop, physics, input handler, save format or change to production/Yandex. Short landscape keeps the established deliberate desk/prop hide for play-space and heading clearance, but uses the same wall/floor assets and geometry on every step.

**Geometry invariants:** A common CSS grid reserves heading, square stage, viewport-contained non-scrolling controls and footer on every scene. The toy's canvas is constrained by its stage container rather than the contents of each step's panel. The backdrop and workbench stay in a stable stacking order behind the interactive surface; the floor/desk position follows only the stage rectangle, which no longer changes on step transitions. The shared desktop control track is tall enough to show Decor's full continue button. Heading and user controls remain above artwork, and art has `pointer-events:none`. Material selection on Finish is checked through its real buttons rather than assuming its canvas is an interactive hit target.

**Owner-device correction pass:** The subsequent desktop/phone owner screenshots exposed issues that the first geometry-only gate did not reject: the edit tray itself scrolled, the `5 / 6` step label stretched into a pale full-width strip, the complete desk was clipped/painted as if it sank under the floor, Squeeze remained too small on desktop, the floor texture was oversized, and the phone Library cabinet floated above the wall/floor seam. The Pages CSS now keeps edit controls non-scrolling, tightens compact Decor controls, renders a compact step pill (and hides it when empty in Squeeze), preserves the full desk as foreground art over the floor, gives desktop Squeeze its own larger hero scale, scales the floor texture proportionally, and anchors the phone cabinet to the fixed floor seam. Craft-stage canvas/table/floor geometry remains invariant; Squeeze is intentionally allowed a larger canvas.

They need a later recut/re-export with transparent safe margins and cleaner scene boundaries. Runtime layout may position and scale these originals, but should not accumulate masks/crops that pretend the source art is clean.
